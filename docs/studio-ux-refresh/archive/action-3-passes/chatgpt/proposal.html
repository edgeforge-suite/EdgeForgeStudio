EdgeForge Studio UX Refresh Proposal

A frontend-first target state for the CRUD authoring wizard: compact contract inventories, one focused editor, deterministic helper affordances, stronger format identity, and a reviewer-ready shell.

ThesisStop treating each contract as a long page. Treat contracts, handoffs, entities, rules, and review findings as a governed resource registry with a focused inspector.
Primary fixSteps 4 and 5 move from always-expanded forms to compact inventory + detail inspector + impact rail.
Entity model fixMake identity roles exception-based: show active roles, hide repetitive “No role,” and keep field facts in a compact matrix.
Guardrail stanceNo Engine behavior changes, no new manifest shape, no AI-to-manifest writes. Deterministic defaults are suggestions unless already derivable from explicit inputs.

Converged proposal

Studio becomes a Contract Cockpit, not a stack of forms

The 8-step wizard stays as the governed sequence, but each step gets a compact resource surface. Users scan first, edit one thing at a time, and review impact before export.

One shellOne selected itemExplicit review

Target information architecture

Top level remains: Project Setup → Upstream Contract → Entity Model → Data Handoffs → Downstream Interfaces → Rules & Mappings → Review → Export & Build.

Inside each authoring step: Summary strip → Resource registry → Focus inspector → Impact/advisory rail.

Cross-step lenses: Contract map, compact review drawer, deterministic suggestions, evidence/provenance notes, manifest impact.

Key interaction model

Scan: compact list/table shows every contract/handoff/entity with type, status, canonical link, and review state.

Select: one resource opens in the inspector. Tabs replace duplicated repeated form sections.

Derive: deterministic defaults appear as visible chips and suggestions, never silent guesses.

Commit: save/continue validates the same manifest-compatible data already used today.

Pain 1: long pages

Data Handoffs and Downstream Interfaces become compact registries. The selected row/card is the only expanded item. Multiple contracts scale by list length, not by full-form height.

Pain 2: dense Entity Model

Identity roles become exception-based. Default “No role” rows are visually de-emphasized or hidden; behavior copy moves to an inspector and compact impact chips.

Pain 3: visual monotony

Every contract type gets a stable color, icon, short code, and structural card pattern. SOAP, CSV, XML, REST, staging, and Kafka become visually separable at scan speed.

Pain 4: derive, don’t retype

“Derived from source” chips show values obtained from explicit inputs: WSDL service/port/binding/operation, XSD element paths, CSV headers, fixed-width layout fields, identity-role primary key, and generated DDL preview. Ambiguous matches remain suggestions.

Pain 5: structural backend coupling

Design around it with capability badges: “Entity-impacting source” for OpenAPI ingestion; “Manifest reference only” for file/XML/SOAP upstream and downstream. The UI tells the truth instead of implying non-REST contracts will populate entities.

Phased, safe, reversible

Implementation strategy

Move the UX without moving the Engine boundary. Each phase can ship behind a feature flag and fall back to the current forms.

Low-risk rolloutNo generated output change
Phase 1
Visual system + status language.
Type chips, format accents, deterministic-derived chips, manifest-impact chips, revised left nav counts, compact summary strip. Apply first to Upstream because it already has the best compact data model.
CSS/component layer
Phase 2
Registry + inspector for Steps 5 and 4.
Keep existing form fields, but render them inside selected-resource tabs. Store exactly the same project/manifest data. The old expanded rendering remains behind a fallback flag.
Frontend-first
Phase 3
Entity matrix + identity inspector.
Replace per-row behavior prose with impact chips and a side inspector. Hide/default “No role” details until requested. Existing identity role values are untouched.
No Engine change
Phase 4
Deterministic defaults helper.
Optional helper parses explicit pasted/uploaded WSDL/XSD/CSV/layout content and returns structured candidates. UI shows candidates as reviewable suggestions; no automatic manifest write for ambiguous mapping.
Contained helper
Phase 5
Lightweight map lens + review drawer refinement.
Add the topology overview after the registries exist. It reads existing project state only and links to selected resources.
Read-only lens first

Guardrail checklist

Frontend-first: major value comes from layout, components, tabs, filters, and rendering.
Manifest-compatible: no new manifest semantics; same contract/handoff/entity/rule data is edited.
Engine/KS protected: helper returns deterministic candidates only; Engine generation stays unchanged.
Deterministic-not-assumptive: derived values are from explicit input content; ambiguous values remain suggestions.
Phased/reversible: every step can be feature-flagged and rolled back to existing forms.

What this intentionally does not solve

It does not make file/XML/SOAP upstream contracts populate entities, and it does not make downstream contracts source canonical entities. The UI makes that structural boundary visible through capability badges and impact rails.

It does not redesign the Kafka archetype or KA accept/edit/reject loop. Those remain scoped out of this proposal package.

Maintainer decisions

Open decisions to resolve before build

These should be decided explicitly; the proposal does not assume them.

Do not guess
1
Inspector placement: should the focused editor be an in-page center pane, a right drawer, or both depending on viewport? The mock uses in-page panes for desktop stability.
2
Deterministic helper boundary: should WSDL/XSD/CSV parsing run purely in the browser from pasted content, or through a small backend helper that returns structured candidates?
3
Suggestion application: should exact deterministic matches auto-fill as draft rows, or appear as an explicit “Apply selected suggestions” action? Safer default: explicit action.
4
Project persistence: should derived metadata be persisted as project UI state for faster reopen, or recomputed from source content each session when available?
5
Type palette naming: finalize the canonical UI type names: REST/OpenAPI, CSV/delimited, Fixed-width, XML/XSD, SOAP/WSDL, Staging table, Kafka/event.
6
Review posture: keep Review as a soft approval/no export gate, or introduce optional project policy profiles later? This proposal preserves soft review.
7
Map lens phase: ship registry/inspector first, or include the read-only topology map in the same release? Safer default: registry first, map second.

End of proposal package. The mockups above are intentionally one package for maintainer review, not an iterative polish pass.
