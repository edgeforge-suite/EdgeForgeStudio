## Studio dependency surface (from `requirements.txt`)

Studio is a **single-stack Python** web app — no JavaScript build / `package.json`,
so there is **no separate npm dependency surface**. The declared deps are:

- **Runtime:** `fastapi`, `starlette`, `uvicorn[standard]`, `jinja2`,
  `python-multipart`, `pyyaml`, `ruamel.yaml`, `pydantic`, `fastmcp`, `httpx`, `jsonschema`,
  `openpyxl`, `pdfplumber`, `python-docx`.
- **Test-only:** `pytest`, `pytest-asyncio`, `httpx2` (Starlette TestClient backend).

The runtime list intentionally matches `requirements.txt`, `pyproject.toml`, and
the Docker image. The document/schema helper libraries (`jsonschema`, `openpyxl`,
`pdfplumber`, `python-docx`) were already installed in the Dockerfile and are now
declared so Docker, SBOM, and license evidence describe the same runtime surface.

## Regeneration

```bash
make sbom
make lock
# or directly:
scripts/generate-dependency-evidence.sh
```

The script installs the **pinned** tools (`cyclonedx-bom==7.3.0`,
`pip-licenses==5.5.5`, `pip-audit==2.9.0`) into an **isolated** venv (so the
tooling never pollutes Studio's own dependency surface), installs Studio's
constrained packaging toolchain and `requirements.txt` into a project venv,
then emits the CycloneDX SBOM
(`cyclonedx-py environment`), license inventories (`pip-licenses`), and a
direct vulnerability report (`pip-audit --no-deps --disable-pip`) over every
fully pinned constraint, including the packaging toolchain. The named tool +
version is recorded inside `sbom.cdx.json` (`metadata.tools`) when generated by
the script.

## CI gate

[`pytest-ci.yml`](../../.github/workflows/pytest-ci.yml) installs dependencies
from `requirements.txt` constrained by [`constraints.txt`](../../constraints.txt),
runs a non-empty pytest subset plus the in-process L2 smoke, and directly audits
every fully pinned constraint plus a transitive license scan. Known vulnerability
findings, incomplete audit coverage, and audit tool/configuration failures fail
the CI job; the license scan runs after a clean strict audit. The committed
evidence currently reports zero known findings. `pip-audit` is a
vulnerability-advisory floor, not proof of complete application security.
Cross-repo Engine/JDK smoke scenarios remain manual/skip-guarded rather than part
of the per-PR CI gate.
